# PMS-272: asociaciones del historial y límites de validación

Revisión realizada el 24/11/2026 con asistencia de ChatGPT/Codex. Fuente examinada: main `7bedd1ad27fcc40d56e021f46b8d0dcd55a3c7fc`; PMS-20, PMS-222/223/224 y PMS-272 en Jira. Esta propuesta corrige asociaciones falsas y estados vacíos engañosos; no constituye aceptación de HU-MAN-06.

## Problema confirmado y cambio propuesto

El servicio anterior incluía tareas de otro activo cuando su título contenía el mismo tipo. Las fallas se asociaban por categoría, descripción o ubicación; una categoría ausente producía `nombre.includes('')`, que siempre es verdadero. Además, una lista de activos vacía generaba un activo QA fijo, errores HTTP se convertían en listas vacías y fechas ausentes se reemplazaban por la fecha actual.

La propuesta admite relaciones explícitas por ID o, solo sin ID, código del activo. Un ID contradictorio prevalece sobre una coincidencia de código. Elimina el activo QA fijo, los actores y estados de intervención inventados y la sustitución de fechas por la fecha actual. Un fallo de consulta muestra un error; un registro sin relación o fecha genera advertencia, y la vista no declara ausencia confirmada de intervenciones cuando los datos son incompletos. El alta usa `creadoEn`, sin confundirlo con la fecha de instalación.

## Límite que mantiene el PR en borrador

`IncidenciaEntity` de main no tiene relación con `ActivoEntity`. El endpoint `/api/historial-activos` tampoco resuelve esta brecha: su consulta devuelve incidencias globales y los campos `codigoActivo` y `activoNombre` son NULL para ellas. No hay evidencia suficiente para asignar una incidencia existente a un activo solo porque sus textos se parecen.

Los campos opcionales de relación que admite el frontend no se presentan como campos ya disponibles en la API de incidencias. Con el contrato actual, las incidencias sin vínculo quedan excluidas y la pantalla informa que el historial puede estar incompleto. Esto puede reducir los resultados respecto de la demo previa. Para aceptar la HU hace falta acordar y persistir una relación real, actualizar el contrato y registrar QA de integración. No se agrega una migración ni se decide retrospectivamente qué activo corresponde a cada incidencia.

## Verificación ejecutada

Se ejecutó `node scripts/test-historial-service.cjs`: 11 pruebas aprobadas sobre los métodos reales del servicio transpilados con TypeScript, sustituyendo el transporte HTTP, Firebase y signals mediante dobles de prueba. Se verifican listas vacías, error de carga, dos activos del mismo tipo, incidencia sin categoría/relación, fallas ajenas, relación positiva, ID contradictorio, error de historial, fechas ausentes, fecha real de alta y vacío válido. Todos los datos utilizados son sintéticos y exclusivos de las pruebas.

También pasó `ngc` con `strictTemplates`, `strictInjectionParameters` y las opciones estrictas del proyecto para el componente de historial, su plantilla y sus dependencias locales. La compilación fue dirigida a ese componente: no es un build completo de la aplicación ni de producción.

No se ejecutaron navegador, backend, MySQL, Firebase real ni pruebas del entorno desplegado. No se verificó el flujo completo con dos usuarios. El PR no modifica main ni despliega código por sí mismo.

## Condiciones de aceptación pendientes

- Relación persistida y comprobable entre incidencia y activo, con regla de captura/migración validada por el equipo.
- Dos activos del mismo tipo: cada historial contiene únicamente sus registros reales.
- Categoría ausente, lista real vacía y errores de backend correctamente diferenciados.
- QA de CA-01/CA-02 con versión identificada, resultados y evidencia, además de build completo y revisión del equipo antes de integrar.
- Incorporar los resultados y límites a PMS-224, al informe vigente y al Anexo A; no marcar PMS-20/PMS-272 Done solo por aprobar estas pruebas aisladas.
